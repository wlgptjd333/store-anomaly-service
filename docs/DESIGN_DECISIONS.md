## 1. 원본 영상을 자르거나 줄이지 않고 그대로 보관

- **다른 방법:** 촬영 직후 동작 부분만 잘라 저장 / 해상도·FPS 를 낮춰 저장 공간 절약
- **고른 방법:** 핸드폰 원본(대부분 1080×1920, 약 60fps)을 그대로 `data/rgb/videos/<clip_id>.mp4` 로 보관.
  자르기·줄이기는 모두 **나중 단계에서 숫자(표)로** 한다.
- **이유**
  - 동작 구간을 어디서 자를지는 처음에 정할 수 없었다. 실제로 누운 동작은 "일어나는 장면을 넣을지"를
    검수 뒤에야 정했다 (7번). 원본을 미리 잘랐다면 다시 찍어야 했다.
  - 60fps 를 30fps 로 줄이는 건 언제든 할 수 있지만, 반대는 불가능하다. 넘어지기·박치기처럼
    0.3초 안에 끝나는 동작이 있어 높은 FPS 를 버리지 않았다.
  - 영상 하나가 모든 결과(Sequence, 그림, 표)의 출발점이라, 원본이 같으면 누가 다시 돌려도 같은 결과가 나온다.
- **근거:** 영상 170개, 5.1GB — 노트북에 충분히 들어가는 크기라 줄일 이유가 없었다.
- **한계:** 원본에는 얼굴이 나와서 Git 에 올리지 않는다 (8번). 영상은 팀 드라이브에서 따로 받아야 한다.

## 2. 원본 Keypoint 와 정규화 값을 함께 저장

- **다른 방법:** 수업처럼 정규화된 38-D Feature 만 저장
- **고른 방법:** Frame 마다 원본 Keypoint 17 × (x, y, conf) 51열 + 정규화 값 + 품질 정보를 한 CSV(159열)에.
- **이유**
  - 정규화하면 "사람이 화면 어디에 있었나", "몸이 얼마나 컸나" 정보가 사라진다.
    넘어짐·이동 같은 동작에는 그 정보가 필요할 수 있다.
  - YOLO 는 영상 170개에 GPU 로도 시간이 걸린다. 원본을 저장해 두면 정규화 방식을 바꿔도
    **YOLO 를 다시 돌리지 않는다.** 실제로 몸 크기 정규화(4번), 구간 추정(7번), 뼈대 그림(8번)은
    모두 저장된 원본 Keypoint 만으로 만들었다.
- **한계:** 파일이 커진다 (Sequence CSV 는 Git 에 올리지 않음).

## 3. Pose 모델로 YOLO11n-pose 사용

- **다른 방법:** MediaPipe Pose (Body Hero 에서 썼던 방식)
- **비교한 결과** (같은 핸드폰 영상 35개, 교과12 실습에서 측정):

  | 모델 | 검출률 | 떨림 (작을수록 안정) | 좌우 뒤바뀜 |
  |---|---|---|---|
  | YOLO11n-pose | 99.9% | 0.0155 | 0.7% |
  | MediaPipe Full (480px) | 99.7% | 0.0048 | 0.19% |

- **결과를 솔직히 보면:** 떨림과 좌우 뒤바뀜은 MediaPipe 가 더 좋았다.
- **그래도 YOLO 를 고른 이유**
  - **여러 사람:** 무인 매장 CCTV 에는 손님이 여러 명 있을 수 있다. YOLO 는 한 장면의 여러 사람을 각각 찾고,
    다음 단계의 추적(ByteTrack)과 바로 이어진다. MediaPipe Pose 는 기본적으로 한 사람용이다.
  - **표준 형식:** COCO 17 Keypoint 는 공개 데이터셋·논문·다른 모델이 함께 쓰는 형식이라,
    나중에 공개 데이터나 다른 Pose 모델로 바꿔 끼우기 쉽다.
  - **GPU 배치 처리:** 수집한 영상을 한꺼번에 처리하는 데 맞다. (Body Hero 는 CPU 실시간 게임이라 MediaPipe 가 맞았다.)
  - **떨림은 뒤에서 줄일 수 있다:** 이동평균(0.2초)으로 충분히 줄어드는 것을 구간 추정에서 확인했다.
- **n(가장 작은) 모델인 이유:** 최종 목표가 매장 PC·Edge 장비(교과13 Jetson)에서의 실시간이라, 작은 모델로 먼저 한계를 본다.
  Pose 성공률이 평균 99.9% 로 충분했다. 정확도가 모자라면 s·m 모델과 비교할 예정.
- **한계:** 측면 영상에서 카메라 반대쪽 손목이 자주 가려진다 (QA 손목 가림 6개).

## 4. 수업 방식(어깨 폭 정규화)에 몸 크기 정규화를 더함

- **수업 방식:** 골반 중심을 원점, 어깨 폭을 1로 맞춤.
- **문제:** 측면에서는 두 어깨가 겹쳐 어깨 폭이 0 에 가까워지고, 그걸로 나눈 값이 튄다.
  **측면 Frame 의 54.6%** 에서 값이 어깨 폭의 5배를 넘었다.
- **고른 방법:** 어깨 폭과 몸통 길이(어깨 중심 ↔ 골반 중심) 중 큰 쪽으로 나눔.
  정면에서 어깨 폭 ≈ 몸통 길이 × 0.70 이라 어깨 폭 / 0.70 과 몸통 길이를 비교.
- **결과:** 튀는 측면 Frame **54.6% → 0.01% 미만.** 수업 방식 값(38-D)도 그대로 함께 저장해 비교할 수 있게 둠.
- **수업 5일차의 이미지 기준 정규화(x/W, y/H)와도 비교** ([정규화 비교 분석](NORMALIZATION_ANALYSIS.md)):
  - 서 있는 자세의 크기 차이: 픽셀 25% · 이미지 기준 23% · 어깨 폭 134% · **몸 크기 7%**
  - 사람 단위 5-fold 동작 분류(Random Forest 고정): 이미지 기준 64.7% · 어깨 폭 64.1% · 몸 크기 72.9% ·
    **몸 크기 + 골반 화면 위치 74.7%**
  - 다른 날 촬영한 S05 시험: 이미지 기준 **38.2%** vs 몸 크기 + 위치 **67.6%** — 카메라 위치가 바뀌면 이미지 기준 좌표는 무너짐
  - 그래서 이미지 기준 값은 원본 보관(픽셀 + 영상 크기로 언제든 계산)에만 쓰고, 학습 Feature 는 몸 크기 + 화면 위치로 정함
- **한계:** 누워서 몸통이 화면 쪽으로 짧아 보이면(정면에서 카메라 방향으로 누움) 기준 길이가 작아진다.

## 5. 라벨은 촬영 시각으로 자동, 사람이 검수

- **다른 방법:** 영상 170개를 사람이 하나씩 보고 이름 붙이기
- **고른 방법:** 촬영 순서를 미리 정해 두고(동작마다 4명이 차례로), 파일 이름의 촬영 시각으로 동작·사람을 자동 결정.
  늦게 따로 찍은 S05 는 A01 → A17 순서로 정면·측면 2개씩 찍어서, 시간 순서로 정하고 34개가 아니면 멈추게 함.
  그다음 동작별 검수 그림(8명 × 6 시점) 17장으로 사람이 한 번에 확인.
- **이유:** 손으로 붙이면 실수가 섞여도 찾기 어렵다. 규칙으로 붙이고, 사람은 "틀린 것 찾기"만 하는 편이 빠르고 정확하다.
- **결과:** 170개 중 **라벨 오류 0.** 자동 경고 3개는 모두 YOLO 검출 문제였고 라벨은 맞았다.
  검수 중 동작 이름과 실제 촬영 모습이 다른 3개(A08 의자→책상, A15, A16)를 발견해 `filmed_as` 열에 기록.
- **한계:** 촬영 순서가 어긋나면 한꺼번에 틀어진다 → 그래서 사람 검수를 빼지 않는다.

## 6. 품질 검사는 자동 PASS / REVIEW 까지만

- **고른 방법:** 사람을 놓친 비율, 0.2초 이상 연속 놓침, 관절 저신뢰, 다른 사람 검출, 화면 끝 닿음 등
  기준을 숫자로 정해 자동으로 PASS / REVIEW 표시. 다시 찍기·제외는 사람이 영상을 보고 결정.
- **이유:** 데이터가 170개뿐이라 하나 빼는 비용이 크다. 자동 규칙이 "문제 있어 보임"과 "쓸 수 없음"을 구분하지 못한다.
- **결과:** PASS 141 · REVIEW 29. 이어서 수업 5일차 기준의 동작별 QA(11번)와 Human QA 를 했다.
  - 동작별 QA: AUTO_PASS 164 · CHECK 6
  - CHECK 6개를 장면마다 YOLO 상자를 다시 그려 확인: 4개는 화면 가장자리의 문·모니터나 누운 사람의 상체를
    낮은 신뢰도(0.3~0.4)로 "두 번째 사람"으로 잡은 것, 2개는 멀리서 웅크린 순간 몇 Frame 놓친 것.
    학습에 쓰는 사람(가장 높은 신뢰도)은 모두 실제 촬영 대상이었다.
  - **Human QA: PASS 170 · RESHOOT 0 · EXCLUDE 0** → `configs/approved_clip_manifest.csv` 170개
  - 원칙: 데이터가 적어서 "쓸 수 있는 근거가 있으면 쓴다". 다만 근거(무엇을 보고 왜 PASS 인지)는 `human_qa.csv` 에 남긴다.

## 7. 동작 구간은 표로 관리, 일어나는 장면은 뺌

- **다른 방법:** 사람이 170개 영상의 시작·끝을 하나하나 표시 / 영상 전체를 그대로 학습
- **고른 방법:** 공식으로 먼저 추정하고 사람은 고칠 것만 고침 (`segments_auto.csv` 의 `*_final` 열).
  - 시작·끝: 처음 0.5초 자세와 비교한 변화량이 문턱을 넘고 움직임이 멈추는 곳
  - 누움·앉음 동작 6개: 사람 상자 높이로 "일어나기 직전"까지만
- **일어나는 장면을 뺀 이유:** 일어나는 모습은 A07·A15·A16·A17 에 공통으로 나온다.
  넣으면 모델이 동작 자체보다 "일어나기"를 보고 헷갈릴 수 있다. 또 실제 매장에서 알려야 하는 건
  쓰러져 있는 상태이지 일어나는 순간이 아니다.
- **한계:** 누운 뒤 바로 서지 않고 쪼그려 있다가 일어나면 쪼그린 시간이 구간에 남는다 (사람 확인 필요).

## 8. 공개 자료에는 얼굴 대신 관절 뼈대만

- **고른 방법:** README·발표용 그림은 원본 영상 없이 저장된 Keypoint 로 뼈대만 그린다.
  원본 영상·검수 그림·실명 대응표는 Git 에 올리지 않고, 참가자는 S01~S05 로만 쓴다.
- **이유:** 팀원 얼굴은 본인 동의 없이 공개 저장소에 올릴 수 없다. 그리고 모델이 실제로 보는 입력이
  관절 좌표라서 뼈대 그림이 "자세로 판단한다"는 걸 더 잘 보여준다.
- **실무 연결:** 매장 CCTV 서비스에서도 얼굴 영상 대신 관절 좌표만 저장·전송하면 개인정보 부담이 줄어든다.

## 9. 학습·평가는 사람 단위로 나눔

- **다른 방법:** Frame 이나 영상을 무작위로 섞어 Train / Test 로 나누기
- **고른 방법:** Train S01·S02·S03 (102개) / Validation S04 (34개) / Test S05 (34개) — `configs/subject_split.json`
  - Test 를 S05 로 둔 이유: 다른 날 혼자 따로 찍어 옷·조명·촬영 위치가 가장 다르다. 처음 보는 사람·상황에서의
    성능을 가장 엄격하게 본다.
  - 사람·영상 겹침, 빠진 영상, 세트마다 동작 17개가 다 있는지 자동 검사 (`scripts/11_build_subject_split.py`) → 통과.
- **이유:** 같은 사람의 영상이 학습과 시험에 모두 들어가면 모델이 동작이 아니라 그 사람의 체형·옷을 외워도
  점수가 높게 나온다. 실제 매장에는 처음 보는 사람이 온다.
- **한계:** 참가자가 5명뿐이라 Test 한 명의 점수는 흔들릴 수 있다 → 사람마다 한 번씩 Test 가 되는
  Leave-One-Subject-Out 5-fold 목록(`reports/splits/loso_folds.csv`)도 만들어 평균과 편차를 함께 본다.

## 10. 동작 분류: Random Forest Baseline 부터, 수업 방식과 같은 조건에서 비교

자세한 숫자는 [Baseline 성능평가](BASELINE_EVALUATION.md).

- **다른 방법:** 처음부터 시간 순서를 보는 딥러닝(1D-CNN, GRU, LSTM)
- **고른 방법:** 수업 6일차대로 Random Forest Baseline 을 먼저 세움 — 구간 전체를 30단계로 보간해 펼친 Feature
- **이유:**
  - 영상 170개는 딥러닝에 작음. 단순한 모델로 "이 데이터로 어디까지 되나"를 먼저 알아야 복잡한 모델이 정말 나은지 판단할 수 있음
  - 학습이 몇 초라 Feature·창·정규화를 **한 번에 하나씩 바꿔** 9가지를 비교할 수 있었음
  - Feature 중요도로 무엇을 보고 판단했는지 설명할 수 있음
- **평가 규칙:** Validation(S04)과 S01~S04 4-fold 로만 고르고, 다른 날 찍은 S05 Test 는 마지막에 한 번. Random Forest 난수만 바꿔도
  ±0~4%p 흔들려서, 이보다 작은 차이는 "효과 없음"으로 판단
- **근거 숫자:**
  - 3팀 기준 모델(몸 크기 정규화 + 각도 + 골반 위치, 동작 구간): Validation **76.5%**, Test S05 **70.6%**
  - 수업 그대로(어깨 폭 38-D, 영상 전체): Validation 67.6%, Test S05 **55.9%**
  - Sequence vs Static(가운데 Frame 1개): 4-fold 74.3% vs 57.4% → **시간 흐름이 가장 큰 차이**
  - 각도 4개·골반 위치 2개·동작 구간 자르기: 차이가 난수 변동 안 → 효과 있다고 쓰지 않음
  - 확신도 0.30 이상만 자동 판정하면 (Validation 으로 정한 기준) Test 에서 44% 를 100% 정확도로 판정 → 나머지는 사람 확인
- **한계:** Random Forest 는 "몇 번째 단계에 어느 관절이 어디"를 따로 봐서 리듬이 다른 동작(흔들기 vs 밀치기)을 헷갈림.
  다른 날 찍은 측면 영상 5개가 A11(몸통 박치기)로 쏠림 → 카메라 변화에 약함
- **다음:**
  1. 1D-CNN 또는 GRU 를 같은 Split·같은 Dataset 으로 비교 (Body Hero 에서 Conv1D 경험). 복잡한 모델이 Baseline 보다
     편차 이상으로 낫지 않으면 단순한 쪽을 씀. 매장 PC 에서 30FPS 가 나오는지도 기준
  2. **3D 확장:** 비솔 스튜디오에서 같은 주제(무인 매장)의 동작 17개를 VICON 3D 로 찍었다 (D001~D017 = A01~A17 확인, 11/24 해 봄 → 18번).
     여러 각도로 2D 투영해 학습 데이터를 늘리고, "실제 영상만" vs "3D 합성 추가"를 S05 Test 로 비교 — 카메라 변화에 약한 점을 겨냥

## 11. 동작별 중요 관절 QA 는 동작 구간 안에서, 좌우 중 잘 보이는 쪽으로

- **수업 기준 (5일차 27번):** Pose 검출 < 90%, 한 사람만 잡힌 비율 < 90%, 평균 Confidence < 0.5,
  동작의 중요 관절이 Confidence 0.5 미만인 비율 > 20% 중 하나라도 해당하면 CHECK. 이 숫자는 그대로 썼다.
- **중요 관절:** 팔 동작(내려치기·던지기·밀치기·휘두르기·흔들기)은 어깨·팔꿈치·손목, 발차기는 골반·무릎·발목,
  앉기는 골반·무릎·발목, 눕기·쓰러짐은 어깨·골반·무릎, 박치기는 어깨·골반, 구토는 코·어깨·골반,
  무릎 꿇고 꺼내기는 어깨·골반·무릎·손목 (`scripts/09_action_keypoint_qa.py` 의 CRITICAL).
- **바꾼 점 1 — 동작 구간 안에서만:** 영상 앞뒤에 서 있는 시간은 동작 판단과 상관없다. 전체로 보면 누운 동작처럼
  어려운 장면의 비율이 희석되거나, 반대로 들어오고 나가는 장면 때문에 괜히 걸린다.
- **바꾼 점 2 — 좌우 중 잘 보이는 쪽:** 측면에서는 카메라 반대쪽 팔·다리가 몸에 가려지는 게 정상이다.
  양쪽을 다 요구하면 측면 영상 대부분이 걸리고(처음 자동 QA 에서 손목 가림 REVIEW 10개), 다시 찍어도 같다.
  동작은 보이는 쪽 팔·다리로도 판단할 수 있으므로 "적어도 한쪽이 보이면 통과"로 했다.
- **결과:** AUTO_PASS 164 · CHECK 6 (모두 사람 확인 후 PASS, 6번 참고).
- **한계:** 좌우를 구분해야 하는 동작(예: 오른손으로만 던지기)을 나중에 따로 나누면 이 규칙을 다시 봐야 한다.

## 12. 뒷모습은 따로 찍어 한 모델에 함께 학습 (2026-11-23)

## 13. 서비스 모델: ExtraTrees + 변화량·요약 통계 Feature (2026-11-24)

## 14. Pose 모델은 yolo11n 그대로, 나머지 조정도 바꾸지 않음 (2026-11-24 저녁)

- **재현:** `scripts/03_build_sequences.py --pose-model --max-fps --out-dir`, `13 --steps --smooth --seq-dir --out-dir` 로 기본 데이터를 건드리지 않고 만들고, `20_more_improvements.py [이름 일부]` 로 그 설정만 다시 돌림 ([Runbook](RETRAIN_RUNBOOK.md) 2장).

## 17. 1D-CNN 폭 128 (난수 3개 평균), Pose 는 11n 그대로 (2026-11-24 밤)

- **문제:** 16번 이후 안 해 본 것이 많았고, 16번 4-fold(87.9)는 1D-CNN 1개 기준이라 서비스(3개 평균)와 모양이 달랐다.

- **결정:** ExtraTrees + 1D-CNN **폭 128 · 난수 3개 평균**. 4-fold 90.2 → 91.7 ± 0.4 (가장 낮은 사람 83.7 → 85.0, 뒤 82.8 → 83.3),
  고른 뒤 Test S05 86.3 → 88.2. 서비스 분석 시간은 거의 같다 (신경망은 작고 Pose 가 대부분).
  - 미리 정한 기준(+1%p 넘게 + 가장 낮은 사람·뒤도 오름)을 넘은 것 중 서비스 비용이 없는 유일한 것.
- **Pose 11m 을 고르지 않은 이유:** 4-fold 94.0 으로 가장 높았지만 Test S05 85.0 (오히려 낮음) → 다른 날·옷·조명에는 이득이 확인 안 됨.
  CPU 에서 4배 느려 실시간 보기가 5fps 아래로 떨어진다. AI 서버를 GPU 로 돌리게 되면 다시 비교할 후보.
- **기준 30% 유지:** `판단 불확실` 16.2%, 30% 위쪽 정확도 95.9% — 전 모델과 거의 같다.
- **한계:** 여러 설정 중 최고를 고르면 4-fold 숫자가 조금 낙관적이 된다 → Test S05 로 한 번 확인했고, 차이(영상 1개)는 작다고 읽는다.
  남은 약한 동작 A05 밀치기 72%. 더 올리려면 새 사람·장소·카메라 각도 데이터가 필요하다 (모델 쪽 조정은 거의 끝).

## 18. VICON 3D 합성 데이터와 Keypoint 기하 증강은 쓰지 않음 (2026-11-24 밤)

- **문제:** 모델 조정(17번)으로는 더 오르기 어렵고, 약한 곳(새 사람·각도)은 데이터가 모자란 것. 새로 찍지 않고 늘릴 방법이 있나.
- **대안:**
  1. **VICON 3D → 여러 각도 2D 합성** (23번) — 교과12 모션캡처 17동작(1명)을 가상 카메라 8·16방향으로 투영. 각도를 마음대로 만들 수 있음.
  2. **Keypoint 기하 증강** (24번) — 회전 ±10°, 시간 늘이기, 앞뒤 0~15% 자르기, 화면 위치 이동.
  3. 새로 찍기 — 가장 확실하지만 사람·시간이 필요.
- **결정:** 1·2 모두 서비스에 넣지 않음. 미리 정한 기준(+1%p 넘게 + 가장 낮은 사람·뒤도 오름)을 넘은 게 없음.
  - 합성 16방향: 4-fold 91.7 → 91.0. 뒤 +1.0 이지만 S02 88.2 → 82.4. 연기자 1명의 동작 방식 쏠림 + VICON 관절 위치 ≠ YOLO Keypoint 위치 + 가림·잡음 없음.
  - 기하 증강 최고(앞뒤 자르기): 92.5 (+0.8) — 기준 아래, 회전과 합치면 91.5 로 더해지지 않아 변동 안으로 읽음.
- **누설 확인:** 연기자 = 이 저장소 S03(통일 S02, 사용자 확인). S03 이 평가 쪽인 fold 에서는 합성 데이터를 빼서 S03 숫자가 그대로(96.1)인 것을 확인.
- **한계 / 다음:** 3D 가 여러 사람 것이면 결과가 다를 수 있다 (지금은 "1명 3D 로는 안 된다"까지만 확인). 합성 가중치 낮추기·대각선만 쓰기는 안 해 봄.
  다음 개선은 실제 영상 — 서비스 `export_clips` 로 꺼낸 IP Webcam 녹화를 사람이 검수해 더하기 ([Runbook 1-1b](RETRAIN_RUNBOOK.md)).
  교과12 3D 데이터의 원래 쓰임은 VICON(정답 3D) ↔ 웹캠 2D 비교·관절 각도 검증 (교과12 프로젝트).

## 19. 카메라 구도 변화: 증강 대신 그 구도의 실제 영상을 학습에 더함 (2026-11-24 밤)

- **문제:** 팀원(S05)이 다른 구도(가로 화면, 높은 곳 대각선)로 찍은 5개를 서비스가 2/5 만 맞힘. 같은 사람이라 원인은 구도.
  4-fold 는 모두 같은 촬영 구도라 이 약점을 못 잡음 → 새 구도 5개를 따로 평가 세트로 만들어(25번) 같이 봄(26번).
- **대안:** (1) 골반 화면 위치 Feature 빼기 (2) 시점 증강 (2D 좌표를 가로·세로로 늘여 다른 각도 흉내) (3) 앞뒤 자르기
  (4) 조합 (5) VICON 3D 합성 + 위치 빼기 (6) 새 구도 실제 영상을 학습에 더하기.
- **결정:** (6). (1)~(5)는 새 구도 맞힌 수가 모두 2/5 그대로, 정답 확률은 최고 +5%p 인데 그 후보들은 4-fold 가 2~3%p 떨어짐.
  (6)은 4-fold 91.7 → 92.3, 뒤 83.3 → 84.8, 가장 낮은 사람 85.0 → 86.9 로 기존 평가를 해치지 않음.
- **근거 수치:** [Baseline 성능평가 5-8](BASELINE_EVALUATION.md) 표. 골반 위치를 빼면 4-fold 가 3%p 떨어짐 → 같은 구도에서는 쓸모 있는 정보라 유지.
- **한계:** 새 구도 영상이 5개(한 사람·한 장소·동작 5개)뿐이고, 학습에 넣었으므로 그 구도 정확도는 더 잴 수 없음.
  다른 장소·높이에서는 여전히 떨어질 수 있음. 다음 새 구도 영상은 **평가 먼저(25번) → 그다음 학습**. 서비스 `export_clips` 로 꺼낸 녹화도 같은 순서.

## 20. Feature 이름·좌우 반전은 `src/schema.py` 한 곳에서 (2026-11-25)

- **문제:** 관절 17개 이름이 7개 스크립트(08·13·14·15·17·20·23)에, 각도 4개·골반 위치·body40 이 4~5곳에, 좌우 반전이 2가지 방식(17번 DataFrame 반복문, 20번 행렬)으로,
  번호 붙은 스크립트 불러오는 importlib 3~5줄이 11개 스크립트에 따로 있었다. 한 곳만 고치면 학습·서비스 Feature 가 어긋날 수 있음.
- **결정:** `src/schema.py`(KP·ANGLES·POS·BODY40·`seq_columns`·`flip_matrix`) 하나로 모으고 서비스는 같은 파일을 복사해 씀(`update_model.sh` 가 같은지 확인).
  스크립트 불러오기는 `src/common.load_script` (한 번만 실행, 여러 스크립트가 같은 파일을 불러도 다시 안 돌림). 15번의 구도 실험 옵션(`--no-pos`·`--view-aug`·`--crop-aug`)은 19번 결정대로 안 쓰므로 삭제.
- **확인:** 예전 코드(HEAD)와 이름 목록이 모두 같고, 255개 Sequence 반전 결과가 17번·20번 예전 함수와 비트 단위로 같음. 15번 재실행 → ExtraTrees·1D-CNN 가중치까지 예전 서비스 모델과 같음 (Val 96.1 / Test S05 88.2).
- **찾은 것 (한계):** 같은 값이라도 배열 메모리 배치(행 우선 C / 열 우선 F)가 다르면 1D-CNN 정규화의 float32 평균 마지막 자리가 달라지고, 그 차이만으로
  Val 96.1 → 98.0, Test S05 88.2 → 84.3 으로 바뀌었다. 15번은 예전과 같은 열 우선 배치로 맞춰 재현성을 지킴.
  즉 **사람 1명(51개) 평가 숫자는 학습 잡음만으로 ±4%p 움직인다** → 모델 비교는 지금처럼 4-fold·난수 여러 개 평균으로 하고, Test S05 한 숫자로 고르지 않는다.
